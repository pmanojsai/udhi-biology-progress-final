# Udhi Technologies — Frontend Developer Intern Assignment

You are building the complete first version of the Udhi Technologies frontend assignment described below.

Treat this as a **real professional frontend submission**, not a quick demo. The final result should be polished enough to submit to a frontend engineering team, while staying within the scope of the assignment.

## 1. Assignment goal

Udhi Technologies is building an AI-powered learning platform for UK GCSE students.

We need to build **one responsive student progress screen** for a GCSE Biology student.

The screen must answer two questions immediately:

1. **Where does the student stand?**
2. **What should the student do next?**

There is deliberately no provided design. The quality of the product thinking, information hierarchy, UI decisions and frontend implementation are important.

Do NOT turn this into a generic dashboard with eight identical topic cards.

The interface should feel like a real, thoughtful GCSE learning product.

# 4. Product direction

Design the screen as a **student decision-making experience**, not an admin dashboard.

The visual hierarchy should tell a story:

### A. Where am I?

Student identity, subject, exam board, exam context and progress summary.

### B. What should I do next?

This should be the strongest visual section on the page.

### C. What do I know?

Show topic progress in meaningful groups rather than eight identical rows.

### D. What haven't I started?

Give untouched topics a distinct "Not started" state.

The most important action should be obvious without requiring the student to study the whole page.

---

# 5. Recommended page structure

Build the following information hierarchy.

## Header / student context

Show:

* Priya
* Biology
* AQA
* GCSE Biology context
* Exam date
* Dynamically calculated days until exam

The exam countdown must be derived from the supplied exam date rather than hardcoded.

Use a clear, calm, premium education-product aesthetic.

Do not make the header overly large.

---

## Progress overview

Create a concise progress snapshot.

Useful metrics can include:

* average mastery across started topics
* topics started
* strong/mastered topics
* topics not started

If calculating average mastery, explicitly label it as being calculated from **started topics only**.

Do NOT silently include untouched topics as zero knowledge.

Do not invent unsupported metrics such as predicted GCSE grade, exam score prediction, probability of passing, readiness percentage, etc.

Only derive metrics that are defensible from the supplied data.

# 6. "Your Next Move" — primary hero section

This is the most important section.

Create a visually prominent section such as:

### Respiration

23% mastery

Relevant supporting information:

# 7. Recommendation logic

Do NOT hardcode:

```ts
recommendedTopic = "Respiration";
```

Instead, derive the recommendation from the topic data.

Use a simple, transparent heuristic that considers:

* lower mastery
* fewer questions attempted
* how long it has been since the topic was studied

The exact implementation is your engineering decision, but it must be deterministic and explainable.

Respiration should naturally emerge as the strongest recommendation from the supplied dataset because it has:

* very low mastery
* only 6 questions attempted
* the oldest studied date among started topics

Transport in Cells should be a secondary concern.

Cell Division and the stronger topics should not be incorrectly presented as the highest priority.

Do not make the heuristic unnecessarily complicated.

Create the recommendation logic in a dedicated utility/module rather than embedding it directly inside the page JSX.

---

# 8. Not-started topics — critical edge case

This is extremely important.

Homeostasis and Inheritance have:

```text
mastery = 0
questionsAttempted = 0
lastStudied = null
```

Do NOT display:

> Homeostasis — 0% mastery

as though we know the student has zero knowledge.

The data only establishes that the student has not started these topics.

Create a distinct state:

### Not started

**Homeostasis**

No questions attempted yet

**Start topic →**

And similarly for Inheritance.

The UI should make "Not started" visually and semantically different from a weak topic.

Do not classify a topic as not started based solely on mastery === 0.

Use the absence of activity, e.g. zero questions and null lastStudied, as the meaningful signal.
